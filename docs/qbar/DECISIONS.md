# Qbar 语义层：决策记录

每条都写「结论 / 理由 / 被否的方案」。改代码前先读这里，别把否掉的方案又捡回来。

## D1 语义层建在自建索引上，不建在 Everything 上
- **结论**：翻译层输出 `QbarSearchSpec`，由 `NativeSearchIndex.SearchSpec` 求值。
- **理由**：仓库里 Everything 集成已经整体移除（QbarProviders.cs:176 注释、全仓无 SDK 调用），
  没有 SetSort / SetMax / 正则开关可用。任务书第 12 节的兜底条款要求「写清缺什么 + 用替代方案继续」。
- **被否**：把 Everything64.dll 重新引进来 —— 等于给项目加一个外部依赖和一套索引副本，
  与「不读写 Everything 索引、不起第二个实例」的红线方向相反。

## D2 保留 Everything 风格查询串，但只作诊断
- **结论**：翻译层同时产出 `EverythingText`（ext:/size:/dm:/! 写法）并显示在调试面板，
  执行走 Spec。
- **理由**：这串东西人读得懂（`doc: 报表` → `ext:c;chm;…;xml 报表`），排障时一眼看出展开了什么；
  将来真要接回 Everything，只换执行层。
- **被否**：让自建索引去解析 Everything 语法 —— 那等于在索引内核里再写一个解析器，两套真相。

## D3 索引快照升到 v2，加 size 与 mtime
- **结论**：`NameSizeKb`（uint，KB 饱和）+ `NameDay`（ushort，自 2000-01-01 的天数，65535 = 未知）。
- **理由**：`size:`/`date:` 谓词是核心语法，若查询时对候选回盘 stat，2000 条候选就是 2000 次 IO，
  端到端 50ms 预算直接崩。快照多两列数组，38 万文件约 1.5MB + 0.8MB。
- **被否**：查询时 stat（慢）；只存排序键不存大小（`size:` 没法精确过滤）。

## D4 拼音与子序列：自建 CJK 名字索引 + 窗口内模糊，两路混合
- **结论**：
  - 拼音（`yh`/`yinhang` → 银行）：自建索引，只收名字含汉字的条目，存「首字母串 + 全拼串」，
    查询走前缀 > 全拼前缀 > 全拼子序列三档打分。
  - 子序列（`rprt` → report）：`NativeSearchIndex.FuzzyScan` 在索引名字上扫子序列，
    只在「纯关键词 + 结果数 < FuzzyThreshold(12) + 查询像英文缩写」时启用。
- **理由**：Everything 类内核本来就不做拼音/子序列，只能自己补。全量扫描 38 万条名字做子序列
  约 10ms 量级、且只在结果稀疏时触发，比"常驻一张全量模糊索引"划算得多。
- **被否**：
  - (b) 仅扩大窗口到 20000 再本地模糊 —— 命中率仍然为 0（子序列在候选窗口里根本不存在），
    白白多花 5–10ms。
  - 给所有文件建全量拼音+子序列索引 —— 内存翻倍，收益只有 CJK 那不到 10% 的名字。

## D5 拼音索引只存目录引用，不存完整路径
- **结论**：`_dirs[]` + `_names[]`，命中时才 `Path.Combine`。
- **理由**：每条 CJK 名字多拼一条几十字符的新串，30 万条就是几十 MB；目录串是快照里的同一批实例，
  直接引用不额外分配。实测 7867 条估算 1.6MB（见 TESTING）。
- **被否**：存完整路径（内存）；存 (dirIndex,nameIndex) 二元组（省不了多少，还要多一层间接）。

## D6 档位做成加数，不做单独排序阶段
- **结论**：`TierBonusHigh = +120`、`TierBonusLow = -120`，与原生分相加后统一排序。
- **理由**：单独阶段会让「High 里的烂匹配」整体压在「Normal 里的整名命中」上面，用户会觉得搜索变笨。
  120 的跨度约等于「名字子串 vs 名字前缀」的差距，够重排又不至于盖住相关性。
- **被否**：分阶段排序（见上）；把档位乘到分值上（原生分范围 400–1000，乘法会让 High 里的
  低分项反超，语义不可控）。

## D7 回归闸门比「相对顺序」，不比逐位相等
- **结论**：规则全关后跑新引擎 vs 旧入口 `NativeSearchIndex.Search`，检查旧结果的每一条都在、
  且相对顺序不变；额外报「规则重排 N 条」。
- **理由**：增强路径（拼音/子序列）会追加旧入口没有的条目，逐位相等必然红；
  而默认规则开启时顺序本来就该变（用例 11）。只有关掉规则、只比旧结果子序列才是有意义的回归。
- **被否**：逐位相等（误报）；只比命中集合（漏掉"顺序被搞乱"这个最可能的事故）。

## D8 外部程序启动用 ProcessStartInfo(UseShellExecute=true)
- **结论**：`Verb = "runas"` 提权、`WindowStyle=Hidden` 静默、`WorkingDirectory` 指定目录。
- **理由**：.NET 这个封装底下就是 ShellExecuteEx，行为等价（PATH/App Paths 解析、UAC、关联程序），
  net7.0-windows 线同样可用，省一层 P/Invoke 维护。
- **被否**：手写 ShellExecuteExW —— 需要自己管 SEE_MASK_NOASYNC、STA 线程和结构体版本，
  收益是零（唯一区别是能拿到 hProcess，本项目不需要）。

## D9 拼音多音字只取 TinyPinyin 的一个读音
- **结论**：`重庆` 得到 ZHONG QING，`长` 得到 ZHANG。不自建字表。
- **理由**：自建多音字表是长期维护负担（每个词都要人肉标注），而拼音搜索只是"多一条路"，
  首字母串（CQ）通常仍能命中。写进已知限制。

## D10 谓词-only 查询把候选窗口压到 600，且扫描收满即早退
- **结论**：`!spec.HasKeywords` → `window = min(window, 600)`；谓词分支收满 `max(limit*2,600)` 条即停。
- **理由**：没有关键词就没有相关性可排，剩下的只是"名字长度/目录深度"，多取纯浪费；
  未优化时 `-ext:tmp` 264ms、`date:week` 116ms，优化后 2.6ms / 4.2ms。
- **被否**：全量扫描后截断（就是上面那个 264ms）。

## D11 历史只喂建议，不参与文件重排
- **结论**：JSONL 按月一个文件，字段 v/t/kind/surface/name/path/query/rank；只用于空面板「最近/常用」。
- **理由**：一旦让历史影响文件排序，同一份索引在不同人机器上结果不同，回归测试和排障一起失效。
- **被否**：把点击次数做成排序权重（不可解释，且会自我强化）。

## D12 分面只在候选窗口内统计，并明确标注「本页」
- **结论**：`QbarSearchOutcome.Facets` 由 Hits 现算，底栏显示「本页：文档 3 · 文件夹 2」。
- **理由**：为每个桶发一次全量查询会把端到端打到几百毫秒；窗口内统计与用户看到的列表一致。
- **被否**：精确全局计数（慢）；不标注口径（用户会当成全库数量）。

## D13 设置页先做开关，逐条编辑留后续
- **结论**：Qbar 设置页新增「搜索语义层」卡：规则/内置包/拼音/分面/历史/调试面板开关 + 候选窗口 +
  防抖 + 刷新拼音索引 + 规则与命令清单。
- **理由**：排障最需要的是"能不能关掉"，不是"能不能加一条规则"；后者是纯 UI 工作量，
  数据模型（QbarFilter/QbarPriorityRule/QbarCommand）已经可持久化，手工编辑 settings.json 即可生效。
- **被否**：先做完整列表编辑器（工期大、回归风险高，收益排在开关之后）。

## D14 调试面板双入口
- **结论**：设置里勾选 `Search.DebugPanel`，或在 Qbar 里按 Ctrl+D 即时切换。
- **理由**：翻译层出问题时用户往往正在输入框里试，去设置页翻一趟就断了思路。

## D15 增强命中（拼音 / 子序列）必须过同一套优先级闸门
- **结论**：`TryEnhance` 合并拼音与子序列结果前，逐条走 `PassPriority`：DoNotIndex 直接丢、
  Ignored 计入隐藏数、High/Low 照样加减档位分。
- **理由**：自检抓到的真 bug —— 目录设成 DoNotIndex 后，主路径把 190 条剔干净，
  子序列兜底又把 24 条从索引里捞回来，用户会认为「规则不生效」。
  两条路只要有一条绕过规则，规则就不是规则。
- **被否**：增强路径不复用主路径（简单，但等于给规则开后门）；
  增强只在规则全关时启用（牺牲功能换一致性）。

## D16 拼音索引按「估算字节」停收，硬上限 24 MB
- **结论**：`MemoryBudget = 24 MB`，`EstimatedBytes` = 每条 32 字节对象开销 + 三个串的字符数 × 2 + 3 × 26 字节；
  BuildWorker 累加到预算即停收，状态行写明「已达内存上限，只收了一部分」。
- **理由**：条数上限管不住内存 —— 长中文名字每条可到 300 字节，30 万条就是 80+ MB。
  实测 10480 条 = 2.89 MB，按同口径外推 30 万条约 82.8 MB，说明条数上限必须配字节上限。
- **被否**：只限条数（内存不可预测）；不设上限（用户的机器不是我们的实验机）；
  用 `GC.GetTotalMemory` 判断（托管堆几百 MB 时几 MB 的索引埋在里面看不出来，实测差值为 0.0 MB）。

## D17 自检里显式发布夹具快照，不改查询入口的可见性
- **结论**：新增 `NativeSearchIndex.PublishForTest(root)`，把夹具树建成全局快照供引擎/拼音/模糊用例使用。
- **理由**：`SearchInForTest` / `SearchSpecInForTest` 刻意只查临时快照（不污染全局状态），
  而引擎读的是全局快照；为了让测试覆盖真实代码路径，宁可多一个明确的测试钩子，
  也不把搜索内核改成「可注入快照」——那会把只为测试存在的复杂度带进生产路径。
- **被否**：给引擎加 snapshot 参数（生产签名被测试需求牵着走）；
  测试里直接跑 selftest 目录的真实索引（依赖用户磁盘内容，不可重现）。

## D18 接回 Everything SDK 作首选后端，自建索引留作兜底
- **结论**：`EverythingApi`（动态加载 Everything64.dll）+ `QbarEverythingBackend`；
  条件不满足（没装/没运行/索引在建/用户在设置里关掉）就回落到 `NativeSearchIndex.SearchSpec`。
- **理由**：用户明确要求"用 Everything 做本地检索"——那是它擅长的部分（NTFS 索引、几十万文件、
  增量更新），本项目不该维护第二套索引。但只留 Everything 也不行：Everything 未运行/未装时
  搜索会直接空掉，而这层语义（过滤器、优先级、命令、拼音）仍然有价值。双后端是唯一同时满足
  两个要求的做法。`QbarSearchOptions.PreferEverything` 默认 true，设置页可关。
- **被否**：
  - 只用 Everything（没装 = 搜索废掉，且用户手动关掉 Everything 就没了）；
  - 只用自建索引（违背用户指令，且全盘扫描的增量更新永远追不上 Everything）；
  - 把 Everything 索引库读进来自己查（红线 1 明令禁止，而且格式未公开）。

## D19 拿回的候选必须过 `SpecFilter` 本地复核
- **结论**：Everything 只负责"出候选窗口"，每条结果再走 `NativeSearchIndex.SpecFilter.Accept`。
- **理由**：三处语义必然不同 —— ① `MatchPath=TRUE` 让词能命中路径任意段，自建索引只认
  "文件名 + 所在目录"；② `ext:`/`size:` 的边界解释（含不含等号）与 Spec 不完全同口径；
  ③ `dm:` 是本地日期串，跨时区会漂。不复核就会出现"同一个查询换个后端结果就变"，
  回归闸门和用户信任一起崩。复核复用了索引内核的同一批函数，等于让两条路共享一份真相。
- **代价**：2000 条候选逐条过谓词，实测中位 1.1 ms（见 TESTING §3），可以忽略。
- **被否**：
  - 完全信任 Everything（结果集会随 Everything 版本/设置漂移，无法回归）；
  - 把 `wfn:`/`regex:` 也翻译成 Everything 语法（Everything 开全局正则会污染普通词，
    而且它的 `wfn:` 不认我们的 glob 语义）；
  - 复核只做"路径去重"（挡不住语义差异）。

## D20 动态加载 DLL，不把 Everything64.dll 打进发布包
- **结论**：`NativeLibrary.TryLoad` + `TryGetExport` 按候选路径探测；发布包里不带 DLL。
- **理由**：① 没装 Everything 的机器上 `DllImport` 会在首次调用抛 `DllNotFoundException`，
  而要求是"没装就安静降级"；② 捆绑 DLL 会让 `IsAvailable` 恒为真，但用户没装客户端时
  查询必然失败（错误码 2），状态显示反而更难懂；③ 第三方 DLL 的升级责任不该由本项目背。
- **被否**：`DllImport` + 安装包里塞 DLL（见上）；只在 `%ProgramFiles%\Everything` 找
  （便携版/自定义安装会漏，所以补了环境变量与 LocalAppData 两条路径）。

## D21 `RunAsAdmin` 默认改为 true
- **结论**：`AppSettings.RunAsAdmin` 默认 `true`，启动时非管理员就用 `runas` 重启自己（一次 UAC）。
- **理由**：用户明确要求"软件默认以管理员模式启动"。功能上也不是摆设：普通进程的键盘钩子
  收不到更高完整性级别窗口的输入（UIPI），用户对着管理员程序按快捷键会毫无反应且不报错。
- **代价 / 兜底**：
  - 每次升级/首次启动会弹一次 UAC；拒绝后仍以普通权限运行（功能降级，不阻塞）；
  - 命令行/诊断模式**永不**触发提权重启，否则脚本与自检会卡在 UAC 上 ——
    `ElevationHelper.TryRelaunchElevated` 除显式白名单外，还按 `CliFlags.IsDiagnostic` 类别豁免；
  - 逃生开关：环境变量 `CLP_SKIP_ELEVATE=1`，或启动参数 `--noelevate`。
- **被否**：默认不管理员、首次运行再提示（用户已经明说要默认管理员）；
  只对"需要管提权窗口"的场景临时提权（钩子必须在启动时就装好，事后提权要重启，体验更差）。

## D22 候选窗口用"修改时间降序 + 定长窗口"，不做本地排序再回填分页
- **结论**：`SetMax(2000)`（可配 200–20000）、`SetSort(14=DATE_MODIFIED_DESC)`、`SetOffset(0)`；
  本地打分只重排这 2000 条，并在基准/调试里显式报告"缺失 / 多出"。
- **理由**：Everything 的 `SetMax` 是"只要前 N 条"，没有稳定的游标分页（索引随时变，
  第二页与第一页不保证同一快照）。要在本地做全局正确排序，就得把全库命中拉回来（`report` 一次
  158658 条），代价是几十毫秒到上百毫秒的复制与解析 —— 与 50 ms 预算直接冲突。
  取最近修改的 2000 条，符合启动器的主要场景（找刚放过/刚下载的东西），且截断在诊断里可见。
- **代价**：冷门旧文件可能落在窗口外。真机实测 `report` 总命中 2427，本机 39 个旧命中在窗口外，
  基准的回归列因此报"缺失 39/39"（索引里其实有，查 `report.py` 能命中）。
  补救路径：词写具体一点（提高命中精度）、或把窗口调大、或关掉后端用本地索引（本地是全覆盖）。
- **被否**：
  - 名字升序（sort=1）：实测延迟无优势（57.6 ms vs 53.7 ms），且按字母截断更容易把近期文件挤出去；
  - 先本地排序、再让 Everything 分页：SDK 无此能力，且会漏结果；
  - 把窗口默认设成 20000：SDK 扫描成本不变，但复核 + 重排线性变慢（2000 条约 4 ms → 20000 条约 40 ms），默认值上不划算。

## D23 默认优先 Everything，但保留"只用本地索引"开关
- **结论**：`QbarSearchOptions.PreferEverything = true`；设置页与 `INPUTPLUS_DISABLE_EVERYTHING=1`
  都能关掉，关掉后走 `NativeSearchIndex.SearchSpec`。
- **理由**：Everything 覆盖整机（本机 115 万条），本地快照只覆盖用户选的根（38.6 万文件 / 6.9 万目录），
  "文件搜不到"比"慢 5 毫秒"严重得多，所以默认用覆盖面大的那个。但红线 5 的 50 ms 预算在
  115 万条索引 + 子串查询下达不到（实测 p95 54.5 ms，其中 45+ ms 在 SDK 内部），
  必须给一条可预测的退路，且退路要能被基准/回归验证（关掉后 p95 39.2 ms、回归闸门全部一致）。
- **代价**：同一台机器上两种后端的结果集不完全相同（覆盖面不同），需要用户理解这个差异 ——
  所以「后端」一行同时出现在调试面板、状态栏详情与 `--qbar-bench` 输出里。
- **被否**：只留 Everything（老机器超预算且离线/未装时无退路）；只留本地索引（用户明确要求接 Everything）。

## D24 spec 里目录不可能满足时，查询串必须显式带 `file:`
- **结论**：`QbarEverythingBackend.BuildQuery` 只要 `Extensions`/`NegExtensions`/`MinSize`/`MaxSize`
  任一存在（或 `FilesOnly`），就追加 `file:`。
- **理由**：真机跑出的缺陷 —— `-ext:tmp` 在按名字排序时，窗口 600 条**全是目录**（目录名短、
  排序靠前，且目录没有扩展名），复核阶段按 `dirsEligible` 全剔，用户看到的就是"零结果"。
  加上 `file:` 后，候选窗口直接只含文件：两种排序都是 600 候选 / 0 剔除。
- **代价**：查询串多一个谓词；对 Everything 的匹配面没有负面影响（`ext:` 本身就只可能命中文件）。
- **被否**：只靠复核层兜（窗口被无效条目占满时，复核只会把结果清空）；把目录也当文件参与 `ext:`
  （目录没有扩展名，语义上就是错的）。

## D25 单元测试锁本地后端，双后端一致性交给专门用例
- **结论**：`SelfTest.QbarSearch` 里所有构造 `QbarQueryContext` 的夹具都显式 `Options.PreferEverything = false`；
  双后端行为由 `SelfTest.QbarEverything`（25 项）覆盖。
- **理由**：夹具文件是测试里刚写盘的，Everything 的索引有延迟（文件监听 + 批量提交），
  跟随本机是否装了 Everything 会让 `--selftest` 变成"看环境脸色"——真机上就因此红过一次
  （"DoNotIndex 目录的结果被彻底剔除：原始 30 → 剔除后 4，隐藏 24"，因为候选窗口里混进了
  别的 26 个同名文件）。锁本地后端后，6286 项全绿且结果可复现。
- **代价**：本地后端测试不能替代"真机 Everything"验证，所以保留 `--everything-status` 与
  `--qbar-bench` 两条手动/脚本化通道，并在 TESTING §6.4 记录真机数字。
- **被否**：让测试等索引（不确定、CI 上不可用）；给测试环境单独建 Everything 索引（超出范围，且违反红线 1）。

## D26 命令标签排在网址/程序/搜索之后

- **取舍**：`ResolveChip` 的判定顺序是 网址 → 程序 → 搜索 → 命令。自定义命令最后才被认。
- **理由**：`bd`、`gh` 这些搜索引擎关键字是老用户的手感，任何"命令优先"的排列都会让用户
  按空格后拿到一个"执行某条命令"的提示，而他要的是搜索。命令是后来加的能力，
  排最后等于"只有没人认领的关键字才归命令"，升级零破坏。
- **被否**：命令优先（会抢 `bd`，用户必须给命令换关键字才能恢复搜索）；
  给命令加独立前缀（`@ol`）—— 与用户"输入 ol 按空格"的直觉相反。

## D27 自定义命令并进「直接搜索」，不新开分类

- **取舍**：每条 Path 非空的命令在 `ActionCatalog` 里注册成一个 `qcmdsearch:<id>`，
  与 `search:` 引擎动作同属「直接搜索」分类。
- **理由**：用户对「直接搜索」的心智是"选中文字 → 按键 → 去某个地方查"，引擎和命令只是
  "去哪里"不同。并在一起，同一个下拉就能绑键，不用先想"这算搜索还是算命令"。
- **代价**：该分类的条目数从「= 引擎数」变成「= 引擎数 + 有程序的命令数」。
  自检里那条"动作数 = 全部引擎数"因此改成只数 `search:` 前缀 —— 不是放宽，是把两种东西分开数。
- **被否**：单独「命令直达」分类（多一个下拉、多一次选择）；
  只为"搜索引擎类"命令开槽（`{query}` 语义一样，没必要分）。

## D28 搜索设置在「文件搜」标签里集中，不塞右栏

- **取舍**：新增 `Tag="files"` 标签，面板跨两列；切到该标签时左栏条目列表与右栏编辑卡隐藏。
- **理由**：过滤器要编辑 49 项扩展名表、优先级要编辑目录+正则+档位，两者都是"表单"而不是
  "一行一个键值"。右栏只有 360px，塞进去只能靠弹窗/折叠，找东西的成本比切标签高。
  标签本身就是分类，用户从「搜索指令」跳到「文件搜」是一次可预期的心智切换。
- **代价**：该标签下没有"选中条目 → 右侧编辑"的布局，代码里 `Refresh()`/`LoadEntries()`
  必须对 `files` 分支早退，否则会去绑一个隐藏的空列表（已加早退）。
- **被否**：设置里另开一个"文件搜索"窗口（多一层窗口管理，且与 qbar 设置分家）；
  折叠面板（同屏信息太多，滚动到一半就分不清哪块属于哪个功能）。

## D29 内置优先级包照抄 Listary 默认表，逐条可停用，不整体改写

- **取舍**：内置 16 条（Normal 3 / Low 8 / Low 正则 5）进出厂表，每条一个开关写入
  `QbarSearchOptions.DisabledBuiltins`；用户规则仍可覆盖（最长作用域 + 命中正则优先）。
- **理由**：这 16 条正好覆盖「装完系统就有的噪音」——`%SystemRoot%`、`Windows.old`、
  `$WINDOWS.~BT`、`~$xxx.docx` 之类。默认全开能让第一次搜索就"像 Listary"，
  而逐条开关让不想改行为的人能精确关掉某一条，比"一键关掉整个规则包"细。
- **代价**：出厂默认与"改造前结果集完全一致"这条红线冲突 —— 用 `RulesEnabled` 总开关解释：
  老用户想回到原样，取消勾选「按优先级规则重排」即可；自检里比对旧入口时显式关规则包。
- **被否**：只给一个总开关（用户没法只关"系统目录"而保留临时文件降权）；
  把 16 条写进用户规则表（首次启动就 16 条自定义规则，删起来烦）。

## D30 `ol` 做成内置命令，Path 留空、运行期解析

- **取舍**：`QbarCommandStore.Builtins()` 增加 `builtin.dict`（keyword `ol`），
  `Path` 为空；执行时 `FindEudic()` 先扫 PATH 再看四个默认安装位置，
  找不到就开 `https://dict.eudic.net/dicts/en/<词>`。
- **理由**：`ol` 是用户最常用的动作之一，但它依赖"本机装了欧路词典"这个前提。
  写死 `eudic.exe` 会让没装的人只看到「找不到程序」，等于功能不存在；留空 + 网页兜底
  让这条命令在任何机器上都有反馈。顺带把「命令没有配置程序」的文案改成场景化说明。
- **代价**：命令表里多了一条"没有可执行文件"的项，`IsInternalAction` 必须认它，
  否则会被 `Execute` 当成空路径直接拒绝。
- **被否**：让用户自己去设置里加（正是本轮之前的状态，用户直接反馈"ol 不生效"）；
  只开网页词典（装了欧路的人反而多一步）。

## D31 ListView 用独立的 `RowItem.Grid`，不借 ListBox 的 `RowItem`

- **取舍**：新增 `RowItem.Grid`（`TargetType=ListViewItem`，模板里是
  `GridViewRowPresenter Columns="{TemplateBinding GridView.ColumnCollection}"` + hover/选中底色），
  展开窗口的 `ListView` 用它；`RowItem` 保持原样留给所有 ListBox。
- **理由**：`RowItem` 的模板只有一个裸 `ContentPresenter`，套到带 `GridView` 的 ListView 上时，
  ListViewItem 的默认模板（含 `GridViewRowPresenter`）被替换掉，表头还在、每行却只剩
  `Content.ToString()` —— 界面上就是整列 `InputPlus.UI.Windows.QbarExpandWindow+Row`。
- **代价**：多一个样式；行内边距（10,6）与 ListBox 行（10,7）略有差异，视觉上可接受。
- **被否**：改 `RowItem` 让它同时兼容两者（`GridViewRowPresenter` 在纯 ListBox 里不显示内容）；
  给 ListView 关掉自定义样式（丢失主题 hover/选中色，深色下尤其难看）。

## D32 列排序在本地这一屏内做，第三次点击回相关度序

- **取舍**：`SortRows(rows, key, desc)` 对已筛过的 `List<Row>` 原地排序；
  键为 name/folder/date/size/rank；比较用 `DayValue`/`SizeBytes` 原始值并统一以 `Rank` 兜底。
- **理由**：
  1. 排序是"看"的操作，不该重发查询 —— Everything 重查一次 10–40ms，翻个表头就卡一下不值。
  2. 用显示字符串排会得到错序（"2026-1-9" > "2026-07-08"、"10 MB" < "9 KB"），
     而且这种错"看着像对的"，只能靠自检钉住。
  3. 以 `Rank` 兜底 = 稳定排序。否则用户按日期排完再点一个分面，同一天的文件每次顺序都变，
     看起来像在随机跳。
  4. 第三次点击回 `rank`：用户试完排序总要能一键回到"最相关"，不然只能关窗重开。
- **代价**：名称排序只在这 N 条候选内有意义（Everything 取的是修改时间降序前 N 条）。
- **被否**：按名称排序时把 `MaxCandidates` 提到 20000 重查（一次翻表头 100ms+，且窗口一旦变大
  就再也回不去小窗口的延迟）；引入 "sort key" 传到 Everything（SDK 的排序键只有
  name/path/size/date，且换了之后窗口语义变成"按名称前 N 条"，与打分重排冲突）。

## D33 后端为 `off` 时不跑增强（拼音/子序列）

- **取舍**：`QbarSearchEngine.Run` 里 `if (outcome.Backend != "off") TryEnhance(...)`。
- **理由**：增强路径读的是**本地索引快照**（`NativeSearchIndex`），而 `off` 表示
  "Everything 不可用且按设置不回退本地快照"。放它进来就会得到自相矛盾的界面：
  顶部写"不可用，未回退本地快照"，下面却列出 24 条本地命中；更要命的是这些条目
  没有大小/日期（快照里多为默认值），分面全部落进「更早」，用户会以为文件真的那么老。
- **代价**：Everything 没跑时拼音/子序列查询完全没结果，只能看到一条「Everything 没在运行」
  的可点击提示（点它拉起 Everything）。这是有意的：与其给半真半假的结果，不如说清楚缺什么。
- **被否**：保留增强但给行打"本地快照"标记（两套索引混排，大小/日期还缺失，越标越乱）；
  在 `off` 时自动回退本地快照（违背用户"只用 Everything"的选择，且回到改造前的覆盖面幻觉）。

## D34 候选窗口分两趟取（MatchPath 分级）

- **背景**：开 `Everything_SetMatchPath(TRUE)` 才能像本地索引那样"词也能命中路径"，
  但本机 115 万条索引上实测代价是 p95 34.7ms → 56.0ms（Everything 要为每个候选多扫一遍路径）。
- **选择**：第一趟 MatchPath=FALSE（只命中文件名），候选 < 8 条时再补一趟 MatchPath=TRUE 并去重合并。
- **理由**：名字命中是用户 90% 的意图；路径命中主要救"按文件夹名找文件"的场景，那种场景
  第一趟几乎必然空手，正好触发补扫。两趟都是 Everything 原生查询，语义没有新增假设。
- **代价**：稀疏查询多 ~25–30ms（端到端约 37–40ms）；阈值是常量 `TopUpBelow = 8`，
  想更激进可下调（1 = 只补空结果，p95 20.3ms，但 1–7 条命中的查询会丢掉路径召回）。
- **被否**：一直开 MatchPath（p95 56–63ms，超预算）；一直关（按文件夹名搜不到东西，回归）。

## D35 正则查询的去向（整条正则走 Everything，混合走本地）

- **实测**：Everything 1.4.1 没有逐词 `regex:` 语法，`regex:^rep.*\.docx$` 恒 0 命中；
  `Everything_SetRegex(TRUE)` 是**整条查询**的开关，开了以后 ext:/size: 和普通词都会被当正则。
- **选择**：`IsRegexOnly`（只有一条正则、没有任何别的谓词）时原样下发并开全局正则；
  一旦混进普通词或其它谓词，改由本地快照执行，后端标签如实写「本地索引」并说明原因。
- **理由**：两种写法各走它唯一正确的那条路，不猜、不静默降级。
- **代价**：正则 + 普通词的组合只覆盖本地快照（目录范围小于 Everything 全盘）。
- **被否**：把所有查询都关掉 MatchPath 硬凑 50ms（丢掉路径召回）；正则一律走本地（连 `regex:` 单用
  也只能看 D 盘的快照，用户会觉得"正则坏了"）。

## D36 content: 降级为文件名检索，wfn: 改为下发

- **content:** 两条后端都没有内容索引。原来只把它塞进调试串、不进 spec，等于"接受了这个词但
  什么都不筛"（用户看到全盘结果）。现在降级成普通文件名检索并在调试面板标黄说明。
- **wfn:** 原设计不下发（怕 glob 语义不等价），实测后果更糟：查询里只剩 wfn: 时 Everything 收到空查询，
  返回 0 条，本地复核再严也筛不出来。现在下发 `wfn:<glob>`，复核阶段再用同一套 glob 校验一次。
- **引号**：为 wfn:/regex: 加引号走 `QuoteRaw`，只保护空格，**不加倍反斜杠**——
  加倍后 Everything 收到字面双反斜杠，正则/glob 直接失配（实测 0 命中）。

## D37 高亮交给 SDK，不自己算

- `Everything_GetResultHighlightedFileNameW` 返回的串里自带命中区间标记，
  与 Everything 自己的匹配规则完全一致（含大小写折叠、通配）。
- **选择**：解析成 `[起点,长度]` 交给 UI；只有本地索引兜底时才用自己的子串匹配。
- **理由**：自己算会与后端判定不一致（"明明有结果却没有高亮"），且重建字符串有分配成本。
- **代价**：解析函数要能扛半截标记/乱序区间（自检 4 条断言钉住）。


## D38 展开窗口的图标走 ShellIcons，不做"预取全部"

- **问题**：名称列原来只画一个 Segoe 字形，docx/pdf/exe 全长一样，跟资源管理器对不上。
- **做法**：Row 实现 INotifyPropertyChanged，18×18 的 Image 叠在字形上；图标只为**已经生成容器的行**
  请求（ItemContainerGenerator.StatusChanged + ScrollChanged 触发），ShellIcons 缓存命中就同步设，
  否则后台 STA 解析后回调。
- **理由**：2000 行一次性 ExtractIcon 会卡住滚动，而且多数图标用户一眼都不会看。
- **被否**：把所有行图标在查询返回时批量取（滚动卡顿）、改用 SHGetFileInfo 同步取（阻塞 UI 线程）。

## D39 欧路词典定位靠"系统线索"，不靠猜安装目录

- **问题**：用户把欧路装在 D:\software\eudic，而旧实现只扫 PATH 与 Program Files，
  于是查词静默回落到网页词典 —— 用户看到的现象是"查词没实现"。
- **做法**：EudicLocator 依次查 PATH → App Paths 注册表（HKLM/HKCU × 32/64 视图）→
  开始菜单快捷方式（自写 IShellLink+IPersistFile 解析 .lnk）→ 常见目录。
- **理由**：安装路径是用户自由选的，但安装程序一定会留开始菜单快捷方式；注册表与快捷方式
  都比"猜目录"可靠。自写 COM 互操作约 40 行，比引第三方库划算。
- **被否**：全盘扫 eudic.exe（慢且打扰磁盘）、只加 D:\software 到候选目录（治标）。
- **代价**：开始菜单递归枚举在极端臃肿的机器上要几十毫秒；只在打开命令编辑器与执行查词时调，
  不在查询热路径上。

## D40 分面/结果行用 keyed 紧凑样式，不改全局 RowItem

- 分面行 46px、结果行 42px，小窗（600 高）里「最近 30/365 天、更早」直接被裁掉。
- 新增 RowItem.Compact（ListBoxItem）与 RowItem.Grid.Compact（ListViewItem），行高 30px，
  并删掉 TypeList/TimeList 的 MaxHeight 硬限制。
- **理由**：全局 RowItem 是 Qbar 主面板在用的，改它会连带搬动主面板的观感；
  keyed 样式只影响展开窗口。
- **被否**：统一压全局样式（牵连主面板）、加滚动条（用户要的是"小窗也能看全"，不是"能滚到"）。

## D41 内置命令一律可编辑，填了程序就改成启动它

- 旧实现按 IsInternalAction 把「程序/参数/工作目录」整片禁用，用户反馈"内置命令不能编辑"。
- 现在：字段全开；执行时 IsInternalAction 且 Path 为空 → 走内置实现；
  Path 非空 → 当成外部程序启动（参数、工作目录、提权、静默照常生效）。
- **理由**：用户想把 ol 指向自己的欧路、把 newfile 指向自己的模板程序，都是合理诉求；
  "内部实现"应当是默认值，不是枷锁。
- **代价**：内置动作填错程序会得到"启动失败"而不是"什么也没发生"，所以失败文案必须点名命令。

## D42 过滤器保留两种触发写法：空格为主，冒号兼容

- 现状：以前只有 `doc:`（首词以冒号结尾）会变成 chip，用户要求"跟搜索一样打个空格"。
- 决定：`ResolveFilterTrigger` 同时接受 `doc` 与 `doc:`；空格与 Tab 都走这条判断，
  位置排在引擎关键字（cmd/psh/ol…）之后。
- **理由**：老用户的手指记忆是冒号，新用户不会知道有冒号；两种写法解析到同一个过滤器，
  结果完全一致，没有分叉状态。
- **被否**：只留空格写法（会让照着旧文档用的人以为过滤器坏了）。

## D43 展开窗口的表头用共享 keyed 样式，拖动把手平时透明

- 表头原来吃系统 Aero 主题（灰渐变、居中），和设置页的表格完全不是一路。
- 决定：`Theme/Controls.xaml` 新增 `GridView.Header` 与 `GridView.Header.Right`（右对齐给数字列），
  透明底 + 下边框 + 11.5px 三级色 + 左对齐；`PART_HeaderGripper` 自带模板，平时全透明、悬停显一条淡线。
- **理由**：表头是"看数据"的框，不该比数据更抢眼；把手那根深色竖条在浅色表头里会被当成多余的分隔线。
- **被否**：直接套设置页的 `Text.Tertiary` TextBlock（那只是文字样式，没有列头交互与拖动把手）。

## D44 左栏两半等高用星号分配，不用 MaxHeight

- 决定：展开窗口左栏行定义 `Auto / * / Auto / *`，"筛选"与"最近修改"各占一半，
  删掉 TypeList/TimeList 的 MaxHeight。
- **理由**：用户要的是"小窗也能看见全部内容"，MaxHeight 只在窗口够高时才对，窗口一小又变成滚动条。
- **代价**：窗口特别矮（<520 的 MinHeight 以下）时两组会同时出现滚动条，属于极端情况。

## D45 查词命令的参数写进命令表，而不是藏在代码里

- 决定：内置 ol 的 `Parameter` 出厂值 = `-w "{query}"`（常量 `DefaultDictParameter`）；
  运行期两条来源（用户指定程序 / 定位器找到的欧路）都走同一个 `QbarCommandStore.Execute`；
  `Effective()` 给「老配置里参数为空」的内置 ol 补默认值。
- **理由**：参数是用户资产 —— 看得见才能改成 `--word`、`/c` 这类写法。原实现把 `-w` 拼在
  `RunDictionaryCommand` 里，命令卡参数框空着，用户会判断成「没配」；而且「指定程序」那条分支
  走模板、「自动找到欧路」那条直接拼串，同一个命令两套语义。
- **被否**：只在 UI 里显示灰色的假 `-w`（改不了，还是骗人）；给 eudic 单独写一个启动器类
  （命令表已经能表达参数，多一层只为绕开自己的实现）。
- **代价**：用户把参数清空想「打开欧路不带词」时不成立 —— 空参数会被兜底成默认模板。
  换程序时填自己的模板即可。


## D46 过滤器覆盖内置项要"认 Id"，不能只认关键字

- **取舍**：`QbarFilterCatalog.Create` 先按 `Id` 把用户项认领到内置项上（`builtin.doc` 等），
  认领时把内置的 `Keyword` 一起改成用户填的值；第二轮才按关键字覆盖（兼容老配置里
  Id 是 `user.xxx` 但关键字撞内置的项）。
- **理由**：用户把 `doc` 改名成 `WD` 之后，若还按关键字匹配就找不到内置那条，
  结果就是「列表里同时出现旧 doc 和新 WD」+「旧关键字还能用」+「WD 打完不回退输入框」三个 bug
  一起出现。身份是 Id，关键字只是它的一个可变字段。
- **被否**：改名时自动生成新 Id 当自定义项（等于承认它就是一条新过滤器，用户改的是同一件东西）；
  只按关键字 + 名字匹配（名字也能改）。
- **代价**：用户想「保留 doc 再新增一条 WD」不成立 —— 得先复制或换个新关键字。
  这条写进了设置页的关键字冲突提示。

## D47 分面行用 UniformGrid 均分高度

- **取舍**：`TypeList` / `TimeList` 的 ItemsPanel 换成 `UniformGrid Columns=1 Rows=Items.Count`，
  配合 `RowItem.Compact` 的 `VerticalContentAlignment=Stretch`，行高随窗口高度均分。
- **理由**：用户报「只有全屏才看得到最近 30 天 / 365 天」「下面一大片空地方」。固定行高 + MaxHeight
  的组合必然要么裁要么空；表格化的分面本来就该铺满。
- **被否**：加滚动条（能看全但要滚，等于把「填满」变成「藏起来」）；把行高写死得更小
  （小窗能看全，大窗反而更空）。
- **代价**：窗口拉得很高时行距会变松 —— 但那是用户自己拉大的，比裁掉内容好。

## D48 圆角与深浅色只对 DWM 生效，验证必须截屏

- **取舍**：展开窗口的圆角交给 DWM（`DWMWA_WINDOW_CORNER_PREFERENCE=DWMWCP_ROUND`，由
  `WindowChrome.AttachTo` 设置，`zeroFrame: false` 保留那圈承载圆角的 1px 边框），
  XAML 里的 `WindowChrome.CornerRadius=12` 只负责内容裁切。
- **理由**：WPF 自己画的圆角在 Mica / 系统阴影下会和边框打架；DWM 的圆角还能跟着系统设置关掉。
- **验证方式**：`RenderTargetBitmap` 只画 WPF 视觉树，拍不到 DWM 层。所以 `--render` 里加了
  `SaveOnScreen`：把窗口真摆到 (80,80)、`CopyFromScreen` 取窗口矩形外扩 12px 的屏幕像素，
  圆角外侧就是桌面 —— `render-v27` 能直接看到被切掉的角。
- **被否**：`AllowsTransparency=true` 自绘圆角（丢硬件加速、Mica 与阴影全废）；
  只设 `CornerRadius` 不管 DWM（Win11 上仍是直角，用户第一次反馈就是这个）。

## D49 Qbar 面板不记忆过滤器 chip

- **取舍**：`Open()` 每次都 `ResetFilterChip()`，不持久化 `_appliedFilter`。
- **理由**：面板是"临时输入口"，用户关掉再打开的期望是空白。带着上一次的过滤器会让
  「为什么搜不到别的文件」变成一个无法自证的谜。
- **被否**：记住上次过滤器（Listary 也不这么做）；只清输入框保留 chip（更糟：看起来像还在筛）。

## D50 右键缩放的「中间带」按手势收养（边带不可见，不能要求用户瞄准）

- 背景：用户报「有时候只能上下或左右」。实测配置无误，问题在九宫格几何：边带各占 38%、中间带 24%，
  十字区（一边带 + 一轴中间带）占可抓面积的约 42%，落进去就必然单轴。
- 取舍：改 `CenterFraction`（放大中间带）会让「抓边」变难，且中间带是四向扩张、抓上去像在拖整窗；
  改 `SetEdgeToClosestSide`（用对角线选边）会让四角退化成单轴（上一轮刚修掉的 bug）。两条都否掉。
- 采用：只对「一轴中间带」按位移收养，阈值 `ResizeAxesThreshold`（默认 60 物理像素，200% 缩放下约 30 逻辑像素）。
  阈值以内的位移不计入该轴尺寸 —— 代价明确、可预测；用户继续沿该轴拖就会跟手。
- 必须在收养那一帧重算 Offset（中间带的是绝对坐标），这不是优化而是正确性；写死在注释里防回归。
- 开关 `ResizeBothAxes` 默认 true；关掉即完全退回上游九宫格行为，便于对照与排障。

## D51 过滤器做成动作：Id 认身份，只注册 Enabled 的

- 动作 Id 用 `qfilter:<QbarFilter.Id>` / `fsearch:<QbarFilter.Id>`，不拼关键字 —— 用户随时会把 `doc` 改成 `WD`，
  拼关键字的 Id 一改就散架（上一轮 D46 已经因为「认名字」踩过一次）。
- 不复用 `QbarRequested` 的字符串预填：那条协议只认引擎表（`TryMakeChip`），过滤器要变成 chip 必须走
  `ApplyFilter`（清输入框、亮 chip、重查）。硬凑前缀会在「过滤器关键字与引擎同名」时打架。
- 只注册 `Enabled` 的过滤器；关掉不注册，避免绑上一个只会打开空面板的键。
- 「直接搜索」侧复用 `SearchSelection` 的取词链（三层提示、Ctrl+C 保底、超长截断到 300 字），不另写一条 ——
  否则「读不到选区」时两条路的体验会不一样。

## D52 查词只留一个出口（DictionaryLauncher），命令模板优先于自动定位

- 背景：查词原来散在三处 —— 内置 `ol` 自己找欧路并硬拼 `-w`、「用户指定程序」走参数模板、定位失败再开网页。
  三处行为不一致：模板被绕过、参数不可见、提示文案各写一份，改一处另外两处照旧。
- 取舍：把「先问用户命令、再问定位器、最后开网页」做成 `DictionaryLauncher.Launch` 一条链。
  用户命令的 `Path` / `Parameter` / `WorkingDirectory` 优先（换别的词典也成立），参数留空才补出厂 `-w "{query}"`。
- 被否方案：①把网页兜底做成「提示用户没装」—— 查词这条路上多数人只想看一眼词义，一次点击的网页比一句
  「请先安装欧路」有用；②在内置命令里写死欧路路径 —— 换机器 / 非默认安装目录立刻失效，1.7.1 已经因为
  只扫 Program Files 踩过一次。
- 取词也合并成 `ActionContext.TryCaptureWord`：三层提示、Ctrl+C 保底、超长截断都在这里，搜文件与查词共用。
  代价是两边的长度上限变成参数（300 / 120），可接受。
- 自检必须在无副作用的前提下跑：`DictionaryLauncher` 留 `FindProgramForTest` / `ExecuteForTest` /
  `OpenWebForTest` 三个钩子，测试不启动任何进程 —— 真机上欧路装着的，跑测试弹词典窗口是最糟的副作用。

## D53 改名可以，但旧关键字必须继续能用（别名而不是「旧名失效」）

**背景**：v1.7.4 把过滤器合并改成「认 Id 不认关键字」，顺手让改名后的旧关键字失效。真实配置里用户把六条内置过滤器
全改成拼音缩写（wd / tp / sp / yp / wj / wjj），结果 `doc:` `file:` `folder:` 三条出厂语法当场全废，
`file: report` 甚至把 1922 条真实命中全剔掉。

**决定**：内置六条各自保留出厂关键字作为别名，`doc:` 与 `wd:` 指向同一条；chip 上仍显示用户改过的名字。

**为什么不选「旧名失效」**：改名是提速，不是遗弃；验收用例 4 明确要求 `doc:` 可用，一次改名就永久破坏它太脆。
**为什么不选「改名时提示会破坏旧名」**：用户已经改完在用了，提示等于把成本推回给用户。
**为什么别名不进设置**：进了设置就多出六条「看不见的过滤器」，还会和「恢复默认」打架；别名是代码里的常量，
指向内置 Id，天然不会漂移。
**副作用**：自定义过滤器不能占用内置别名（`_byKeyword` 优先于 `_byAlias`，用户自建 doc 仍会盖住内置 doc）—— 这是想要的：
关键字是用户资产，别名只是兜底。

## D54 停用项必须留在目录里，不能合并时跳过

**背景**：`Create` 里 `if (!item.Enabled) continue;` 看似无害，实际让 `Override` 把 `Enabled` 写死为 true，
设置页的开关点完刷新又弹回来，内置项还继续参与查询。

**决定**：停用项照样进合并结果（`Enabled=false`），翻译层遇到停用过滤器整条忽略并留一行诊断。
**为什么不是「停用即从目录消失」**：那样设置页就再也看不到它、也无法重新启用，等于删除。
**为什么整条忽略而不是降级成普通词**：降级会让 `doc: 报表` 搜「doc:」字面量并命中 0，比不搜更让人困惑。

## D55 两个只读诊断开关（--settings-dump / --qbar-command）

**背景**：真机排障时只能看到「设置页显示 A、搜索按 B 走」。四份文档写了半天降级策略，到了现场仍缺一条
「把程序实际读到的设置打出来」的路。

**决定**：新增两个只读开关，都写 `%TEMP%` 同时打到 stdout；`--qbar-command` 只解析不执行。
**为什么只读**：诊断开关一旦有副作用（弹 UAC、开进程），用户就不敢在被要求「跑一下这个」时跑。
**被否方案**：在设置页加「导出当前配置」按钮 —— 它只能证明界面那份，证明不了搜索层读到的那份。
